# Golden Test Suite — Infinite Tower (v0.7 engine)

Freezes function-level combat math from the web engine (`js/core.js`,
`js/combat.js`, `js/map.js`) so a Godot/GDScript port can be verified
number-for-number against it. **The engine is the truth being frozen** —
nothing here judges whether a formula is "correct", only that it stays
identical.

## Files

- `golden.js` — zero-dependency node runner + probe implementations +
  case definitions. Never modifies engine files.
- `golden-cases.json` — the frozen expectations (regenerated by `--update`).

## Run

```bash
node tests/golden.js            # PASS/FAIL per category, exit 1 on any fail
node tests/golden.js --update   # re-freeze expectations after an intentional
                                # engine rebalance (never to "make it pass")
```

## How it works

1. `golden.js` loads the real engine files headless (`vm.runInThisContext`
   with `window`/`localStorage` stubs and no `document`; combat.js's
   `HAS_DOM` guard handles the rest).
2. Per case, `Math.random` is swapped for `mulberry32(case.seed)` and
   restored after — the only nondeterminism in these engine paths.
3. Each case names a **probe** (`fn`) — a narrow wrapper over the engine's
   public surface (`IT.*`, `IT.combat.*`, `IT.map.*`). Battleground math
   that has no public function (rawDmg, hitEnemy, dmgHero) is driven
   through real micro-battles via `IT.combat.start(cfg)` and read back from
   the engine's own observables: the returned result, `IT.combat.lastUsage`,
   `IT.combat.debug().lines` (damage numbers are in the log text), and the
   live hero objects in `IT.S`.
4. The probe return value is deep-compared **exactly** against `expect`.

Test skills are data rows injected into `IT.SKILLS` (only documented spec
fields); test heroes are plain objects with explicit stats/axes/trait.
Battles run with `IT.combat.FAST = true` and, by default,
`IT.combat.REACTIONS = false` (the engine's own test hook) so numbers
isolate the system under test; reaction-layer cases opt in with
`args.reactions: true`.

## JSON convention (for the GDScript port)

The header `meta` block in `golden-cases.json` is self-describing: engine
file hashes, the exact mulberry32 implementation, and the conventions list.
Each case is `{id, category, fn, seed, args, expect, note}`:

- Pure-arithmetic cases (`floor_rewards`, `exp_need`, `decide`, `make_enemies`,
  `scout_cost`, `cost_hooks`, ...) need no RNG — a port implements the
  formula in `note` and compares directly.
- Seeded battle cases additionally require reproducing the engine's
  Math.random **consumption order** (AI jitter draws, variance rolls,
  targeting picks). Same seed + same call order = same numbers.

## Engine gaps found while building this (frozen as-is, not patched)

1. **Mend double-scales** — `castSkill` computes
   `round((18 + eAtk*1.6 + lvl*2) * spec.power)` with Mend's
   `spec.power = 1.6`, so atk effectively scales ×2.56 (`heal-001..003`).
2. **Hero-side burn never decays** — `tickHeroStatuses` decrements only
   non-burn statuses, so a burn on a hero ticks every turn for the rest of
   the battle (`bar-005/006`). Enemy-side burn decays normally.
3. **100% barrier still leaks 1** — the final `max(1, ...)` floor applies
   after barrier reduction, so Vanish's full barrier takes exactly 1 damage
   (`bar-002`).
4. **`hp` of cfg.enemies is ignored** — `normalizeEnemies` always starts
   enemies at full `maxHp`; "already wounded enemy" setups must be produced
   by fighting a round first (workaround used throughout).
5. `rawDmg`/`hitEnemy`/`dmgHero` are not exported — observable-behavior
   workaround only; no engine change made.
